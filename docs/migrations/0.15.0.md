# 0.15.0 — one vault format, imported in one pass

Everything below describes what a workspace should **look like** at 0.15.0. A workspace created at
0.15.0 or later already looks like this and needs nothing here.

## Step 1 — an old vault is imported (a tool; nothing to decide)

The vault is `keys/secrets.json` in the standard shape — `{"_readme": "...", "secrets": {"<name>": "<value>"}}`,
names `<scope>.<system>[.<sub>].<field>` — read and written only through `.joserah/tools/secret.js`.

`migrate.js`, which `/joserah:update` runs, imports anything else it finds in `keys/` once:

- a JSON file in a vault's shape (`vault.json`, `passwords.json`): a name → value map of any nesting —
  `corlu → cam1 → user` becomes `corlu.cam1.user`. A collector's record array
  (`[{ system, kind, username, value, ... }]`) needs a scope, so it is listed under `vault.needsPrefix`
  for the owner to run `secret.js --import keys/<file> --prefix <scope>`;
- a `.env` file (`KEY=value`, `export KEY="..."` — the name becomes `env.<key>`);
- a `secrets.json` that is not in the standard shape: it is moved to `secrets.json.imported-<date>` first,
  then imported into a fresh standard store.

**One pass, and the assistant does not open the files.** The import runs inside `secret.js --import`;
the migrate report and the journal carry counts and file names, never a value. A cleanly imported
file stays where it is (since 0.15.1 — never renamed, never moved) and is recorded in `config.json` under
`vault.imported`, so no later run reads it again; the owner deletes it once satisfied. Only
`keys/` is read: a module's own `.env` (under `docker-stack/`, a project) is that module's secret and is
left where it is. Key files (`id_ed25519`, `*.pem`) are not vaults and are left alone.

**What is never touched (0.15.1).** A file that `.mcp.json` or `.claude/settings*.json` names is in use
(`vault.inUse`) and is not even opened. `secret.js` refuses, and migrate lists under `vault.notVault`
with the reason, a service-account key (`"type": "service_account"` or a `private_key` field), PEM or
OpenSSH content, a file over 512 KB, and a JSON of any other shape. 0.15.0 renamed a cleanly imported
file to `<name>.imported-<date>`; a workspace that already has such a file keeps it as it is — nothing
renames it back. If something (an MCP server, a script) read that file under its old name, say so to the
owner: they rename it back by hand, and the vault already holds its values.

**If an import skipped entries** — a name that already exists with a different value, an empty value, a
key that makes no valid name — the file stays as it is and is listed under `vault.kept`. The owner
resolves each with `--set <name> --force` or `--rename <old> <new>`, then runs
`node .joserah/tools/secret.js --import keys/<file>` again. Existing values are never overwritten.

## Step 2 — the names-only index (a tool)

`.joserah/vault-index.md` lists every name, grouped by scope, and no value. `secret.js` rewrites it
after every change; migrate writes it once. It is the one vault file the assistant reads; `keys/`
stays denied.

## Step 3 — `ownerIsDeveloper` is gone (a tool, then one line if wanted)

The config key that switched the session briefing to technical talk is removed from the plugin; the
briefing's default — match the owner, volunteer no internals they did not ask for — holds for everyone.
`migrate.js` deletes a leftover key from `config.json` by a narrow text edit (`configKeysRemoved` in its
report). A workspace whose owner builds this software and wants files, tools, commits and versions
named plainly writes that as one line in its own `.joserah/directives.md`.

---

## When this is done

Stamp `migratedTo` at the installed version (`/joserah:update` step 3b has the command), then run
doctor. `structure migrations applied` should stop warning, and a second update imports nothing.
