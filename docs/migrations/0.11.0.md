# 0.11.0 — source material out of the way, numbers as claims, and a pass that reads the notes

This is the first structure note. Everything below describes what a workspace should **look like**
at 0.11.0 — not what the plugin's code does. Run through it in order; each step says whether it is a
command or a decision.

A workspace created at 0.11.0 or later already looks like this and needs nothing here.

---

## What a workspace looks like at this version

```
<workspace>/
├── AGENTS.md · .gitignore · .claude/settings.json    plugin-owned
├── projects/          {Owner}/{ProjectName}/ — never tracked; each has its own git
├── imports/           source material and working files — outside the repository backup
├── keys/              SENSITIVE
└── .joserah/
    ├── config.json · directives.md · conventions.md · learned.md
    ├── tools/ · desk/ · knowledge/ · personal/ · user/
    └── conversations/    session transcripts — outside the backup
```

Three things distinguish it from earlier layouts:

1. **`imports/` at the workspace root**, not `raw/` and not `.joserah/knowledge/raw/`. Dated folders
   sit directly under it. It is deliberately outside the repository backup: bulky and regenerable.
2. **Load-bearing numbers are claim lines**, not sentences — `- [measurement|calculation|decision|estimate]
   <subject> -> <value>` with `condition:` · `date:` · `by:` · `source:` underneath. A superseded claim
   is struck through and points at its successor rather than being deleted.
3. **`config.json` carries `migratedTo` and `lastSweep`** — what structure the workspace has caught up
   to, and when its content was last read.

---

## Step 1 — move the source material (command)

If `raw/` sits at the workspace root, or `raw/` under `.joserah/knowledge/`:

```
node "${CLAUDE_PLUGIN_ROOT}/tools/relocate.js" <workspace-root>
```

One command from either historical location; it flattens the dated folders and rewrites every link
that cited the old path. Afterwards run `node .joserah/tools/verify-links.js` and fix any break
before going on.

**The owner may decline this one.** Some workspaces keep `raw/` at the root deliberately. If they
do, that is a decision, not a pending migration: record it in `.joserah/directives.md` in one line so
doctor's warning is understood rather than re-litigated every session, and treat this step as done.

## Step 2 — decide the backup scope (decision)

`imports/` and `.joserah/conversations/` are outside the repository backup at this version. Anything
in there that cannot be regenerated has no copy anywhere else. Ask the owner, once: is there material
under `imports/` that must survive losing this machine? If yes, it belongs in a project with its own
git, or in whatever off-machine copy they already keep — not in the knowledge base.

## Step 3 — the content is not migrated by any of this (decision, then a long job)

Steps 1 and 2 move the shell. The pages themselves still hold their numbers as prose: the workspace
now understands claims and has none. Nothing in `update` will ever change that — it does not read
notes.

Offer `/joserah:sweep`. Say plainly what it costs: the first sweep reads every page in the knowledge
base and is hours of delegated work; every later one reads only what changed since. It is the owner's
call whether to run it now, run it in pieces, or leave the older pages as prose and let the sweep
pick them up when they are next touched.

Do not stamp `lastSweep` on their behalf if they decline — an unswept workspace should keep saying so.

---

## When this is done

Stamp `migratedTo` at the installed version (`/joserah:update` step 3b has the command), then run
doctor. `structure migrations applied` should stop warning; `knowledge sweep` will keep warning until
a sweep actually runs, which is correct.
