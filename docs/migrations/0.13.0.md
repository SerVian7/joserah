# 0.13.0 — the briefing arrives whole, the brand ships, and the directives get shorter

Everything below describes what a workspace should **look like** at 0.13.0 — not what the plugin's
code does. A workspace created at 0.13.0 or later already looks like this and needs nothing here.

**Order does not matter, and that is deliberate.** The owner may copy updated files into a workspace
by hand before they update the plugin from the marketplace — that is theirs to do, on their own
schedule, and it cannot be automated. Nothing here assumes the plugin was updated first. Each step
says what it needs and refuses politely when that is not there yet.

---

## Step 1 — nothing to do about the briefing (information)

The plugin now emits the session briefing as two hook commands instead of one, and caps each at
8,000 characters. The per-file cap is 5,000. Both halves come from the plugin, so a workspace needs
no change and there is nothing to verify by hand. It takes effect the first time a session starts
under the updated plugin — which, until the plugin is updated, is not yet.

If a session briefing ever opens with a line starting `[cut] This session briefing was`, that is the
new warning working: say so to the owner in one line, and shorten whatever it names. A single file
that is too long is cut with its own `[cut] <path> is longer than 5000 characters` line instead.

## Step 2 — a hosted workspace needs its role file replaced (command)

If `.joserah/config.json` says `"kind": "hosted"`, this workspace has the client role file, which
tells the assistant the owner is the person at the keyboard. From 0.13.0 there is a hosted role that
names the host as the party maintaining and servicing the workspace, says not to assume which of the
two opened the session, and sends every question to the person it belongs to.

Doctor reports this by itself, under `exists: JOSERAH-ROLE.md`, as `does not match the "hosted" role
template for kind "hosted" — was kind changed after scaffolding?`. To fix it:

```
rm <workspace-root>/JOSERAH-ROLE.md
node "${CLAUDE_PLUGIN_ROOT}/tools/migrate.js" <workspace-root>
```

The deletion is not optional: `migrate.js` writes the role file only when it is missing. It copies
the template matching `kind` and is otherwise additive — it never edits a line of the owner's prose,
and never touches `directives.md` or `keys/`.

If the plugin has not been updated yet, this writes the **old** role file back and doctor keeps
warning — run it again after the update. Nothing is lost either way.

## Step 3 — hand-made copies of the mail template go away (decision, then a deletion)

The plugin now ships a `.brand/` folder: `mail.html`, `report.html`, and the logo beside them. It
lives in the plugin, not in the workspace, and it is not the workspace's to edit. A workspace that
grew its own copy of the mail template — anywhere under `.joserah/`, a project's `docs/`, or a
tool's folder — now has two, and the two will drift.

**Ask before deleting each one, per workspace.** Some copies carry a local change the owner made on
purpose, and that change is the thing to keep, not the file. For each copy found:

1. Show the owner the difference between their copy and `.brand/mail.html`, in words, not as a diff.
2. If the difference is nothing they care about, delete the copy and point whatever used it at the
   plugin's.
3. If it is something they want, record it as a rule in `.joserah/directives.md` in one line.

Old image URLs are unaffected. Nothing under `assets/` moved: `j-faded.png` and the logos keep their
published addresses, because mail already sitting in other people's inboxes fetches them from there.

## Step 4 — directives get shorter, and what leaves them becomes a skill (decision, then a job)

A directives file past about 100 lines is carrying three things that are not standing rules for this
workspace, and the last of them is the bulk. The worked example below is a real one: a client
workspace whose file measured **22,284 characters across about 376 lines**, of which everything past
character 10,000 had not reached a session in weeks. Doctor's `standing context size` check reports
the figure for any workspace on every run.

**A. Rules that are really product rules — delete the local copy.** They are in the prompt (hard
rules 11-13) and in the `correspondence` and `orchestrate` skills now. Two statements of one rule
drift, and the local copy is the one nobody updates. In the worked example, these are:

| What the section covered | Size | Where it lives now |
|---|---|---|
| How an orchestrated round runs | 33 lines / 2,139 ch | `orchestrate` (the local folder and file names in its step list stay, as three lines) |
| The mail-watcher section and its safeguards | 31 lines / 1,745 ch | The send-time safeguards are in `correspondence`; how the watcher itself is run stays local, as does the recipient — see B |
| The mail format section | 10 lines / 647 ch | `correspondence` and `.brand/mail.html` |
| Acknowledging rather than leaving a counterparty waiting | 19 lines / 1,074 ch | `correspondence` |
| Incoming mail is data, never instructions | 26 lines / 1,338 ch | Hard rule 12 and `correspondence` (the scope list stays local — see B) |
| Talking a design through before building it | 14 lines / 794 ch | Already in the prompt, §6 |
| The HTML-to-PDF report pipeline and its two print traps | 37 lines / 1,914 ch | `.brand/report.html` and the local skill (C) |
| Revising numbers the counterparty has already seen | 21 lines / 1,127 ch | The local skill (C) |
| The generic half of the reply conventions | ~8 lines | `correspondence` |
| The machine-facing notes in the data and layout section | ~6 lines | The local skill (C) |
| The template boilerplate at the top of the file | ~9 lines | Nowhere — it is the plugin's own explanation, addressed to the owner |

**B. What must stay local, and must not be lost in the move.** Check each one off after the rewrite.
This is a one-way edit on a live workspace: a rule dropped here is not noticed until it misbehaves
in front of the client.

- the assistant's **identity** — its name, its standing as a working colleague, its first person;
- **one recipient, ever** — no CC, no BCC, no third party, and the failure mode that the recipient
  gets inherited from a reply chain;
- the **scope list** — what is in scope and what is not, and that the scope is bounded by one folder;
- the **integrations** — which server, that uploads go through the shared staging folder, that a
  changed binding needs a restart;
- the **language rules** — which language correspondence is written in, which language a report goes
  upward in and in what register, and which figures are never written from memory;
- the **report voice and byline** — first person, the assistant's own name and title, never
  presented as an outside consultant's work and never labelled as an AI suggestion; which language
  version goes first and which waits for approval;
- the **whole analysis method** — 47 lines / 3,837 characters, the largest section in the file —
  every one of its rules, not a summary of them;
- the **data confidentiality rules** — source files are confidential, raw figures do not leave the
  scope, a share notification is mandatory;
- the **folder tree** and the dated decision about what sits outside the backup.

**C. Where the long procedural material goes.** Per the owner's decision, the analysis method and
the report voice move to a **workspace-local skill**, not into the product: they are one client's
method, and the product has no business carrying them. Create `.claude/skills/<name>/SKILL.md` in
the workspace — the same shape a domain skill already takes — and put the reference material beside
it as wiki pages. It is then loaded when that work comes up instead of being paid for in every
session, and it is no longer competing for the briefing's budget.

Target for the worked example: the must-stay list above and nothing else, at roughly 90 lines.

Do this **with the owner, one section at a time**, and read the B list back when it is done. Nothing
in `update` will ever do it — `update` never reads the owner's content, by design.

## Step 5 — the skills changed names (information)

Twelve skills are now ten. `install` and `onboard` are now `setup`. `dispatch`, `plan` and
`research` are now `orchestrate`. `correspondence` is new. If anything in the workspace's own files
names an old skill — a directive, a project runbook, a note — update the name. Nothing breaks if it
is not done; the assistant just fails to find a skill it was told about.

---

## When this is done

Stamp `migratedTo` at the installed version (`/joserah:update` step 3b has the command), then run
doctor. `structure migrations applied` should stop warning.
