# 0.13.1 — the outside plugin is no longer needed, and an owner who builds this can say so

Everything below describes what a workspace should **look like** at 0.13.1 — not what the plugin's
code does. A workspace created at 0.13.1 or later already looks like this and needs nothing here.

**Order does not matter, and that is deliberate.** The owner may copy updated files into a workspace
by hand before they update the plugin from the marketplace — that is theirs to do, on their own
schedule, and it cannot be automated. Nothing here assumes the plugin was updated first. Each step
says what it needs and refuses politely when that is not there yet.

---

## Step 1 — the third-party plugin is no longer a prerequisite (information)

Until 0.13.1 the `project` skill told every session to run two skills belonging to another plugin
before it touched the filesystem, and `/joserah:setup` stopped and refused to continue in a
workspace where that plugin was not installed. Both are gone. Joserah now ships the one planning
step it actually wanted — name the size of the job, stop for a yes, and write a plan file only for
the largest — and depends on nothing outside itself.

Nothing to do in the workspace. If the other plugin was installed only because Joserah asked for
it, it can be uninstalled; nothing here reads it any more. If it is installed for other reasons,
leave it — Joserah neither uses it nor minds it.

## Step 2 — a workspace whose owner builds this software says so (decision, then one edit)

The session briefing used to tell every assistant that the owner is **not** a developer of this
software, and to volunteer no file paths, tool names or version numbers. That is right for a client
and wrong for the person building the thing: it made the assistant talk around the work instead of
about it, and it contradicted the standing instructions, which have always excepted "unless they
ask, or they are the developer".

From 0.13.1 the default line says how much to say rather than what the person is — match them,
speak at the level they speak, do not volunteer internals they did not ask for. Nothing to do to
get that; it arrives with the plugin.

The other half is a decision, and it is one per workspace. If the owner of this workspace is a
developer of Joserah itself, add one key to `.joserah/config.json` by hand:

```json
"ownerIsDeveloper": true
```

The briefing then names files, tools, commits and versions plainly. Nothing writes the key and
nothing removes it — absent is the default, and absent is correct for every workspace but a
developer's own.

**A client's workspace must not have this key.** Neither must a workspace held for someone else, or
a hosted one where the person at the keyboard may be the host rather than the owner. It says one
thing about one person; set it only where that person is the one who will read the answer.

## Step 3 — the signature loses its middle dot (information, then one edit per guest workspace)

Both shipped templates were rebuilt at 0.13.1. The top line of a mail is now the subject alone —
`Bakım Bildirimi`, not `Joserah · bakım bildirimi` — and the signature is the assistant's name, a
space, then `Joserah` a shade fainter, with nothing between the two words. An assistant with no
name is Joserah and still signs `Joserah` once. In plain text, where the faint tone cannot be
carried, it is written `Yarkın, Joserah`.

Nothing to do for the templates themselves: they live in the plugin and arrive with it. A
workspace that grew its **own** copy of the mail template is covered by `docs/migrations/0.13.0.md`
step 3 — show the owner what their copy differs in, delete it, and point whatever used it at
`.brand/mail.html`. The new format comes with that deletion and needs no separate step here.

**The part that does need a hand is `.joserah/directives.md`.** A workspace that wrote its own
correspondence rules may state the old signature literally — a line reading
*signed Yarkın · Joserah*, or a mail-format section that spells out the middle dot. That file is
the workspace's own, and this plugin neither reads nor edits it. In a **guest** workspace we
cannot reach it at all: the confinement that makes a guest workspace safe is exactly what stops us. So the edit is
that workspace's own assistant's to make, on its own machine:

1. Search `.joserah/directives.md` for the assistant's name next to `Joserah`.
2. Replace the joined form with the name, a space, and `Joserah` — or, if the line is describing
   plain text, with the comma form.
3. Delete the rule outright if it was only restating the product rule. `correspondence` now says
   it, and two statements of one rule drift.

Until that is done the workspace signs the old way, and nothing warns about it — a directive
outranks a skill, which is the whole point of directives.

## When this is done

Stamp `migratedTo` at the installed version (`/joserah:update` step 3b has the command), then run
doctor. `structure migrations applied` should stop warning.
